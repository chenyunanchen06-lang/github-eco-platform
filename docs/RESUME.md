## 三、每条结论的证据来源（面试被追问时用）

| 简历里的话 | 实测数字 | 复现方式 |
|---|---|---|

| 原始数据 7.4 GB | 7,415.3 MB | 同上输出的「原始 gz」 |
| 事实表 1,490 万行 | 14,906,594 行 | `python scripts/ods_to_dwd.py` |
| 维度表 402 万行 | 2,431,749 + 1,594,347 | 同上 |

| 提速 4.9x | 510.9s → 103.3s | 见下方「性能优化的完整对比」 |
| 质量校验 5/5 | 5 条全通过 | `python scripts/dq_check.py`（报告落 `reports/dq_report.json`） |
| 波动中位数 24.9% | 均值 35.4% / σ 30.9% | `dq_check.py` R4 的注释与输出 |
| 机器人占 20.5% | 人类 79.47% / 机器人 20.53% | Text-to-SQL 问「机器人账号占多少比例」 |

### 性能优化的完整对比（面试最爱问这个）

| 处理方式 | 事实表构建耗时 | 结果 |
|---|---|---|
| 一次性全量（1,013 万行） | **510.9s** | 稳定复现 `java.lang.OutOfMemoryError` |
| **按天增量（每天一个作业）** | **103.3s** | 稳定跑通，**提速 4.9x** |

**要能讲清为什么**：一次性处理要对全量数据做 `partitionBy("dt")` 写出，
排序 + shuffle 的内存峰值把 JVM 堆打满；按天切分后每批只有 ~150 万行，
内存压力降一个数量级，而且这正是真实数仓里「日批增量」的标准形态。

> ⚠️ 注意：**不要把它说成"分布式优化"**。这是单机 PySpark，优化手段是
> 分批 + 减少重复解析，不是加节点。面试官问"你集群几个节点"时如实说单机。

## 五、面试高频追问与准备

**Q：为什么用 DuckDB 而不用 ClickHouse / Hive？**
A：数据量在单机可处理范围内（1,490 万行 / 519 MB），DuckDB 零运维、直接查 Parquet、
启动快。换成 ClickHouse 要多维护一个服务，收益不明显。如果是 TB 级或需要高并发
点查，我会换 ClickHouse。

**Q：数仓为什么要分 ODS / DWD / ADS 三层？**
A：ODS 保原样可重放、解耦上游变化；DWD 做清洗与统一语义（比如把 15 种事件的
异构 payload 打平成一张事实表）；ADS 面向具体消费场景预聚合。
分层的本质是**让每一层只解决一个问题**，出问题时能定位到具体层。

**Q：数据质量阈值怎么定的？**
A：**量出来的，不是经验值。** 日环比最初写 ±30%，实测中位数就 24.9%，
等于隔天告警一次，属于告警疲劳。按 mean + 2σ ≈ 97.3% 标定成 100%。
> 这题答好了非常加分——它区分「照抄模板」和「理解规则目的」。

**Q：遇到过什么数据源的问题？**
A：三个，都有具体证据：
1. GitHub Archive 的**小时位不补零**，`2026-09-12-00.json.gz` 返回 404，
   正确写法是 `-0`；
2. `HEAD` 请求返回 403，必须用 `GET`；
3. **高频访问会被限流**（403），我加了全局限速器（相邻请求间隔 0.8s）+
   指数退避重试。

**Q：数据源有什么坑是你没想到的？**
A：**两个字段被上游裁剪了，导致两张表做不出来**：
- 原计划用 `payload.pull_request.base.repo.language` 做语言趋势，
  实测发现 GitHub Archive 把 `pull_request` 裁成只剩 base/head/id/number/url，
  `base.repo` 里**没有 language**——全量 1,490 万条里只有 3,612 条带语言（0.04%）；
- 原计划用 `pull_request.merged` 判合并，**同样 0% 非空**。

修正后：语言维度砍掉，改用 `payload.action == "merged"` 作合并信号，
把「语言趋势表」换成「PR 漏斗表」（实测合并率稳定在 92.2%）。
> **这题是全场最值钱的一题。** 主动说出"我原以为能做、实测发现做不了、
> 于是换了方案"，比"我做了 6 张表"更能证明你真的动过数据。

**Q：Text-to-SQL 怎么防止模型乱写 SQL？**
A：三层。① **只读护栏**——正则拦掉 `insert/update/delete/drop/copy/install`
等所有写操作关键字，且必须以 `SELECT`/`WITH` 开头；② **执行报错回灌**——
SQL 报错时把数据库原始错误信息塞回对话让模型改，最多 3 轮
（模型第一次常写错列名，看到 `Binder Error: column "xxx" not found` 后基本能自纠）；
③ **拒答**——3 轮仍失败就明确报错，不返回任何数据。

**Q：为什么不直接用 LangChain？**
A：整条链路就是「一次 HTTP + 一次 SQL + 一个重试循环」，用 `requests` 40 行够了。
引入框架会让依赖变重，而且**它封装掉的恰好是出问题时最需要看见的部分**。
